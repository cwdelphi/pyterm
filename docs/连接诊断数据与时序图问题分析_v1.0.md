# 连接诊断数据与时序图问题分析 v1.0

- 日期：2026-09-25
- 范围：连接诊断（timeline）报表数据 + Mermaid 时序图渲染，覆盖 9 条远程连接配置（SSH×7 / VNC×2，直连共享 WS × 3、网关模式 × 6）
- 数据来源：`autotest/conn-diag-audit.mjs` 模拟浏览器真实连接，拦截 17 份 `/api/timeline/report` 载荷（`/tmp/opencode/audit/reports.json`）+ 9 条 records/detail（`details.json`）+ 详情页截图（`diag/*.png`）

## 1. 结论概览

共锁定 **10 项问题**，按性质分四类：

| 类别 | 问题 | 严重度 |
|---|---|---|
| 数据正确性 | #1 VNC 假失败（agent_connect_ms=0 被判失败） | 高 |
| 数据正确性 | #2 负时延 duration_dc=-16.2 | 高 |
| 数据正确性 | #3 completed<total 却 success=1 | 高 |
| 数据正确性 | #4 成功判定耦合 i18n 文案 | 中 |
| 数据正确性 | #5 派生 error_stage 晚于步骤计算 → failure_analysis 指错步 | 高 |
| 数据正确性 | #8 时间戳不落库（timeline_steps.t_start/t_end 恒 NULL） | 中 |
| 拓扑正确性 | #6 网关模式 step1/6/7 from/to 错标 | 高 |
| 渲染正确性 | #7 图/表过滤 skipped → autonumber 与 step_index 错位 | 高 |
| 渲染正确性 | #10 空字段 wrapper 造成重复/污染上报 | 低 |
| 数据完整性 | #9 ICE/detected_type 字段死代码（采集未上报） | 低 |

另有一项**环境性能观察**（非数据 bug）：网关模式 `duration_ice` 6.6–8.5s 占总时长 95–99%，根因为 WebRTC 侧 STUN 配置不可达（详见 §4）。

## 2. 证据与根因逐项分析

### #1 VNC 假失败（#572 等 3 条记录）— 高

- **现象**：`vnc_lg_ra` 3 条 report 中 `tcp/connect/ssh` 全为 0，但 `agent_ssh_host='192.0.2.50'`（agent 成功诊断已到达），后端仍注入 `error_stage=agent_tcp` 判为失败。
- **根因链**：
  1. agent VNC 成功诊断路径 `signal.go` 用 `time.Since().Milliseconds()`，局域网内耗时 <1ms 被截断为 `agent_connect_ms=0`；
  2. 后端 VNC 成功判定要求 `has_agent_tcp or has_agent_connect`（>0），0 即不满足；
  3. 证据 `agent_ssh_host` 未参与成功判定（仅错误诊断路径也带 host，故不能单独作为证据——但错误诊断必带 `error_stage`，可组合）。
- **修复**：
  - 前端：收到 agent 成功诊断（`_type=="diagnostics"` 且无 `error_stage`）置 `agent_ok=1`，随 report 上报（空 wrapper 消息无 `error_stage` 字段但同时无 agent 字段，加"带 agent 证据"门槛防误置）；
  - 后端：`TimelineReport` 增加 `agent_ok:int=0`；VNC 成功 = `agent_ok or has_agent_tcp or has_agent_connect`；SSH 第一优先级证据加 `or agent_ok`；
  - 证据兜底：`agent_ssh_host 非空 且 error_stage 为空` 也可作为成功诊断到达的证据（错误诊断必带 error_stage）。
  - **不改 agent**（避免重编译+升级链路）。

### #2 负时延 — 高

- **现象**：`vnc-c2c127cd` `duration_dc=-16.2`（t_dc_open < t_rtc_connected）。
- **根因**：打点顺序——`dc.onopen`（webrtc.ts:883）可早于 `connectionstatechange→rtcConnected`（785/835）；差值未钳制。
- **修复**：前端所有 `duration_* = Math.max(0, ...)`；后端 `_clamp_report` 统一钳 `max(0, v)`（防御旧数据/直报 API）。

### #3 completed < total 却 success=1 — 高

- **现象**：直连共享 WS 模式 `duration_ws=0`（`wsOpen` 与 `start` 同 tick）、网关模式 `duration_dc=0`（`rtcConnected` 由 `datachannel_ready` 同步设置，`rtcConnected=dcOpen`，webrtc.ts:640），对应步骤被判 `skipped`，但结果仍 success=1、`completed<total`。
- **根因**：步骤状态门槛用 `duration>0`，而"该阶段是否发生"应看**时间戳字段是否存在**（`t_ws_open`/`t_dc_open` > 0）。
- **修复**：状态 = `failed if error_stage 匹配 else ok if (duration>0 or 对应时间戳>0 or agent 证据>0) else skipped`，**failed 优先**。对应关系：

| 步骤 | ok 条件（或关系） |
|---|---|
| ws | `duration_ws>0 or t_ws_open>0` |
| signal | `duration_signal>0 or t_signal_ok>0` |
| ice | `duration_ice>0 or t_rtc_connected>0` |
| dc | `duration_dc>0 or t_dc_open>0` |
| data | `duration_data>0 or t_first_data>0` |
| agent tcp/ssh/shell | 对应 `agent_*_ms>0 or has_agent_connect or agent_ok` |

### #4 成功判定耦合 i18n — 中

- **现象**：`has_loopback_ok = s.action.startswith(t("timeline.dc_first_byte"))`（api_timeline.py ~L715），切换语言即判定失效。
- **修复**：步骤 dict 增加结构化 `"key"`（如 `loopback`、`dc_first_byte`），判定改 `s["key"]=="loopback" and status=="ok"`；同时 `has_loopback_ok` 改用 report 字段等价条件 `t_first_data>0 or duration_data>0`（不依赖 steps，解除与计算顺序的循环依赖）。

### #5 派生 error_stage 晚于步骤计算 — 高

- **现象**：#572 报表 `success=1 err=''` 但 detail `failure_analysis` 指向 step8（agent_tcp partial），与后端最终注入的 `error_stage=agent_tcp` 不一致；failed 步骤未标。
- **根因**：`_compute_steps` 在 `_judge` 派生 `error_stage` 之前执行，`_finalize_steps` 拿到的 report 尚无 error_stage → failed 标记落空 → `completed` 统计错误 → failure_analysis 退化为 partial。
- **修复**：**两遍计算**——pass1 `_compute_steps(req)` 取证据（含结构化 `key=="loopback"` 判定）→ `_judge_success` 得 `(success, eff_stage, eff_msg)` → 写回 `req.error_stage/error_msg` → pass2 `_compute_steps(req)`（此时 failed 标记正确）。loopback 判定改为 report 字段后可完全在 pass1 完成。

### #6 网关模式拓扑错标 — 高

- **现象/实际链路**（audit 抓包 + handler.go 确认）：
  - 浏览器在网关模式**无 PeerConnection**，二进制帧走 `wsUrl=gatewayUrl`（浏览器直连 gateway 的 wss），gateway↔agent 才是 WebRTC（`handleConnectSuccess` 创建 offer）；
  - `duration_dc` 由 `datachannel_ready` 同步设置（`rtcConnected=dcOpen`）→ 实测 `duration_ice` = **gateway↔agent** WebRTC 建立耗时；
  - 后端步骤却标：step1 `browser→backend`、step6/7 `browser→agent "P2P直连"` → 与真实拓扑不符。
- **修复**（保持 8/11 步结构与文案键复用，改 from/to 与专用文案）：
  - step1：`browser→gateway`（dst=gateway_ip），文案仍 `connect_gateway_request`；
  - step2–5：信令多跳端到端简化，语义基本成立，仅微调方向与 dst_ip（backend→gateway 转发、backend→agent 直发 browser_connect、agent↔gateway 经 backend 的 offer/answer）；
  - step6：`gateway→agent`（src=gateway_ip, dst=agent_ip），文案 `ice_dtls_p2p` 改为「ICE候选协商 + DTLS握手 (网关↔Agent)」；
  - step7：`gateway→agent`，文案 `dc_open` 保持；
  - VNC 网关合并步骤 `p2p_ice_dc` 同改为 `gateway→agent`，文案「WebRTC通道建立 (网关↔Agent)」；
  - 新增/调整 locale 键（`app/locale/zh-CN.json` + `en.json`）：网关 step2/step3 方向修正所需文案。

### #7 图/表过滤 skipped → 编号错位 — 高

- **现象**：详情表 `filter(s => s.status !== 'skipped')`（DiagnosisPanel.vue:251）、Mermaid `buildMermaidCode` 同样过滤 skipped（:97-141）→ `autonumber` 序号与表格 `#`、failure 卡「Step N」（后端 `failed_step=step_index`）三者错位；fallback 文本列表用 `i+1` 而非 `s.index`。
- **修复**：
  - 表格：去掉过滤，skipped 用已有 `.dp-skip` 灰显；
  - Mermaid：**去掉 `autonumber`，label 前缀 `#{{s.index}}`**（即使个别步骤因 from==to 被跳过，编号仍与表格对齐）；skipped 步骤用虚线 `-->>` + ` (skipped)` 后缀画出；
  - fallback 列表：用 `s.index`，去掉 skipped 过滤；
  - `fmtMs(0)` 由 `'-'` 改为 `'0ms'`（0 是有效测量值），`null/undefined → '-'`，负值 → `'0ms'`（旧数据防御）。

### #8 时间戳不落库 — 中

- **现象**：report 载荷带 `t_start/t_ws_open/.../t_first_data/t_error`，但 `connection_timeline` 无 t_* 列、`timeline_steps.t_start/t_end` 从未写入 → 无法回放绝对时间轴。
- **修复**：
  - 写 `timeline_steps.t_start/t_end`（相对 `t_start` 的毫秒偏移，detail 返回）：
    - ws `[0, t_ws_open]`、signal `[t_ws_open, t_signal_ok]`、ice `[t_signal_ok, t_rtc_connected]`、dc `[t_rtc_connected, t_dc_open]`、data `[t_dc_open, t_first_data]`；
    - agent 阶段（tcp/ssh/shell）无浏览器侧绝对时刻 → `0/0`（**不编造**）；
  - `connection_timeline` 不加列（避免 migration 风险；agent 侧时长已有 duration 字段）；
  - 前端补发 `t_error`（model 已有字段，当前未发）。

### #9 采集字段未上报 — 低

- `detectConnType()`（webrtc.ts:784/836）与 `iceLocalType` 等已采集，但 `reportDiagnostic` body 未携带 → `TimelineReport` 也无对应字段（死代码）。本轮**不处理**，记入 backlog（加字段需同步加列+UI 才有价值）。

### #10 空字段 wrapper 重复上报 — 低

- `api_isolated.py:1861` agent_diagnostics 转发存在空字段 wrapper（`{"type":"agent_diagnostics","room_id"...}` 无任何 agent 字段）；每房 2–3 次 report。
- **修复**：前端置 `agent_ok` 必须同时存在 agent 证据字段（防空 wrapper 误置 success）；后端 `_clamp_report` 已有字段级钳制，重复 report 由 `upsert` 幂等覆盖（保留，不改）。

## 3. 环境性能观察：网关模式 ICE 6.6–8.5s（非数据 bug）

- 9 条记录中 6 条网关模式 `duration_ice` 6677–8551ms，占总时长 95–99%（gateway 日志 `ICE room= checking→connected` 印证）。
- 实测（宿主 + gateway 容器）：`stun.l.google.com:19302` 与 `portal.example.com:19302`（=203.0.113.10，即 SERVER_PUBLIC_IP）STUN binding **均 3s 超时**；本机 hairpin 访问自身公网 IP UDP 失败 + Google 国内不可达。
- 影响面：`handler.go` ICE 配置 google STUN 优先 + `auth.py get_ice_servers` 同样含 google STUN → 候选收集/检查被不可达 STUN 拖慢。
- **建议（另行任务，涉及 gateway/agent 重编译与升级链路）**：
  1. ICE 列表移除或降级 `stun.l.google.com`，优先 `stun:203.0.113.10:19302`（本机 coturn，19302/5349/3478/49160-49259 已发布）；
  2. 验证 coturn 从容器内可达性（宿主 STUN 测试脚本消息格式需 20 字节标准头，当前 2 字节测试结果不可信，需用 `turnutils_stunclient`/`stunclient` 复测）；
  3. 同机 gateway↔local-agent 应 <100ms，当前 8.5s 强烈暗示 STUN 等待拖累。
